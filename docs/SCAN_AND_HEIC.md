# HEIC 與「合約級」掃描品質說明

## 本專案 HEIC 處理（效能）

- 優先使用 **`heic-to/next`（Web Worker）**，解碼時較不會讓整個頁面卡住。
- 解碼後**立刻依「圖片長邊上限」縮圖**，再進入壓縮／掃描管線，避免在千萬畫素上跑濾鏡。
- 若仍覺得慢：把長邊上限調低（例如 1600）、或改 iPhone 輸出 JPEG。

## HEIC 為什麼常失敗？

- 瀏覽器**原生大多不解碼 HEIC**，必須用 **WASM / JS 解碼器**（本專案：`heic-to` → `heic2any` → `createImageBitmap` 備援）。
- Apple 持續更新 HEIC 編碼規格，**舊版 libheif** 會出現「format not supported」。
- **建議使用者**：iPhone「設定 → 相機 → 格式」改為 **「最佳相容性」**（輸出 JPEG），最穩定。

## 如何接近「清晰掃描檔」？

純前端能做到的上限與專業掃描 App（OpenCV / ML）不同，建議分層：

### A. 本專案已內建

1. **掃描器模式（OpenCV.js，一律啟用）**：偵測紙張四邊形 → 透視校正 → LAB 空間只強化亮度（CLAHE），盡量保留藍筆等色彩；背景趨近淨白、對比接近平面掃描。  
   - 演算法跑在 **Web Worker**，主頁面可繼續捲動與操作（WASM 不再塞住主執行緒）。  
   - **首次使用**會下載約 10MB+ 的 WASM／JS（Worker chunk）。不支援 Worker 的環境會自動略過 OpenCV，改走輕量備援。  
   - **白紙＋明顯深灰／深色桌面**：會用「邊框平均亮度」估背景、二值化後再以大型**閉運算**把紙內文字孔洞填滿，再取外輪廓，通常比單純 Canny 邊緣更穩；並與 Otsu、多組 Canny 候選比較後取最合理四邊形。  
   - 偵測失敗時會自動改走輕量備援（簡易裁切 → 較強文件加強）。
   - 透視成功後會在主執行緒再做 **色階拉開（polish）**：紙張趨白、對比接近掃描件。
2. **匯入流程**：先以 **較高長邊（約 2600～3400px）+ 高品質 JPEG** 送進掃描管線；完成後再依使用者「圖片壓縮品質」存成列表預覽。**輸出 PDF** 另依「PDF 品質」與較高長邊上限嵌入，與匯入階段解耦。
3. **文件加強（輕量）**：OpenCV 失敗時改為較強對比／亮度濾鏡。
4. **簡易自動裁切（輕量）**：假設**四個角落是單色桌面**，用「從邊緣 flood-fill 背景」估計紙張 bbox（OpenCV 失敗時先於文件加強套用）。  
   - 適合：白紙、深色桌、角落沒被紙擋住。  
   - 不適合：花桌布、紙張貼邊、角落也是紙。

### B. 可再強化的方向（成本較高）

| 能力 | 作法 | 說明 |
|------|------|------|
| 文件偵測 | **ML Kit Document Scanner**（行動 SDK）或 **後端 API** | 最穩，需原生或伺服器 |
| 陰影／不均光 | 進階 OpenCV 或專用演算法 | 比單純 CLAHE 更難調 |
| 超解析度 | 雲端 API 或 onnx 模型 | 成本高 |

### C. 產品與拍攝建議（零程式也有感）

- 光線均勻、避免強烈陰影與反光。
- 紙張盡量占滿畫面、四邊留白給「背景」讓自動裁切有依據。
- 用 **原生掃描 App** 先掃成圖再匯入本工具做 PDF 合併（很多使用者 workflow）。

## 總結

- **HEIC**：已多引擎備援；仍失敗時請改 **JPEG / 最佳相容性**。
- **合約級掃描**：已內建 **OpenCV.js 掃描器模式**；極難場景可再評估 **原生/後端文件偵測**。
